# Application attachments selected while filling the form

Applicants can select private work photos and optional qualifications immediately. Save Draft and Submit coordinate the existing draft RPC, private Storage transfer, attachment RPCs, and final submission; there is no manual draft prerequisite. No migration or hosted configuration change is introduced. Migrations 001–005 and their private bucket setup remain required (see QUALIFICATIONS_SETUP.md).

- New forms support local image previews and PDF open links plus removal before saving. Local object URLs are revoked when selections change/unmount. Files are kept only in page memory, not browser persistence; leaving/reloading the page discards unsaved selections.
- Save Draft validates entered fields/selected attachments, internally saves the draft if needed and attaches the selected files. Empty drafts are allowed. Submit requires 1–3 saved/selected work photos, uploads every selected attachment, then enters pending only after all steps succeed. Certificates are optional; entirely blank qualification rows are ignored, partially entered rows must be completed or removed.
- The form is not keyed by application version, so draft/version updates and recoverable errors do not reset fields or selected files. Busy controls and a synchronous coordinator lock prevent overlapping requests. Status text distinguishes checking, saving, uploading (byte progress), attachment saving and submitting.
- Each queued file keeps its UUID path across retries. Before upload the coordinator checks that private object using Storage `exists`, with the existing applicant SELECT policy. Before attaching, retry reads reconcile records by object path. Confirmed attachments leave the local queue; failed/uncertain files remain. The shared authenticated `transferStorageImage` still uses non-upsert transfers and the existing evidence/qualification RPCs enforce ownership, metadata, count, state and version checks.
- An ambiguous draft/submit response is reconciled against the caller's existing application, expected next version, fields and state before any new save. The application is never duplicated. A completed transfer with a lost response reuses its original object; a completed attachment with a lost response reuses its original record. No upload is automatically deleted on a failed save/unknown attachment result.
- Qualification details/file inputs that have started uploading are held unchanged until retry reconciliation; the selection can still be discarded. Discarding a local selection never deletes a remote file or record. Existing saved records use the existing detach RPC first, then the owner-scoped Storage API cleanup. Attached files remain protected even if a removal/attachment response is lost.
- Refresh saved application explicitly reloads the server version and attached records while keeping entered fields and unconfirmed files. This allows review/retry after another session changes the application, without silently bypassing version checks. A server pending/approved state switches to the existing locked view. Approval RPC, rejection behavior, private buckets, RLS, role authorization and migrations are unchanged.
- Caller-scoped Clean Unused controls remain available for old unreferenced uploads, including abandoned attempts; they never delete attached files. Keep the page open while retrying; after refresh/browser restart, already saved files are loaded from the server and unsaved local files must be selected again.

Local verification uses the existing component/service harness with injected transfers plus all existing PostgreSQL/Auth/Storage-policy fixture suites. New cases cover initial submission with photos/no certificates, empty and attachment-bearing drafts, optional PDF certificates, partial upload failure/retry, completed uploads and attachments with lost responses, lost draft/submit responses, invalid files/counts, duplicate-save prevention, stale versions and immediate controls. These tests do not contact hosted Supabase or prove real Storage HTTP/browser behavior. No deployment or live checks were performed. Before release, repeat first-time and rejected application flows in a test project, interrupt each network step, retry with/without refreshing saved data, and confirm keyboard/mobile file selection and previews.

Recorded local verification (2026-10-27): `npm.cmd test` passed all 84 tests, including PostgreSQL/Storage-policy fixtures; `npm.cmd run build` passed with the existing chunk-size warning. Lint was run locally. No hosted migrations, real Storage uploads or deployment were performed.
