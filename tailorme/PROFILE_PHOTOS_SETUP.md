## Execution order (not applied by this change)

1. Confirm migrations 001-026 are applied to the target project, including 004's optional shop-cover behavior. Do not re-run or edit them.
2. Apply **only** `supabase/migrations/20261031002700_private_profile_avatars.sql` through your normal migration process. It runs in a transaction. No extension, cron job, service-role key, or Auth configuration change is needed.
3. Verify the bucket and authorization checks below before releasing the updated frontend. The frontend now selects `profiles.avatar_path`, so migration 027 must precede the frontend release.

The migration creates `profile-avatars` as **private**, with a 5,242,880-byte limit and JPEG, PNG and WebP MIME allowlist, plus bucket-scoped RLS and restrictive guards. Do not create a second bucket manually or mark this bucket public. Existing `tailor-public` remains public; its existing cover path, upload pipeline and policies are reused unchanged. Personal avatars never appear in shop projections/listings and never use application evidence or styling-preview photos.

Only an owner's `<user UUID>/avatar/<random UUID>.<jpg|png|webp>` path can be uploaded, read, attached or removed. Unique immutable objects are used rather than Storage upserts. `set_profile_avatar(path, expected_path)` locks the owner's profile and checks the previous path; it changes only `avatar_path` and the existing timestamp trigger. No avatar column-update grant, role controls or broad profile-write grant is added. Existing full-name editing and owner-only profile reads remain intact.

The frontend verifies type, size, signature and browser image decoding, then uploads through the existing authenticated Storage transport. Bucket/RLS rules enforce ownership, file length and MIME/extension consistency for direct requests too; server-side image decoding is not provided by SQL/Storage. Display URLs expire after 300 seconds and refresh every 240 seconds/focus. Only paths persist in the database. As with all signed URLs, a holder can use a previously issued URL until it expires.

Save/removal emits an avatar event; PortalProvider refreshes only the avatar field, leaving trusted role state and portal drafts mounted. Cleanup uses the Storage API, only for the caller's unreferenced files. Attachment and deletion serialize on the same advisory key; an ambiguous attachment response cannot cause cleanup to delete the current avatar. Interrupted uploads can be cleaned after one hour from the account page. No SQL deletes Storage objects.
